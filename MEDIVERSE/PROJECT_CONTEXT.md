## 2. PROJECT PURPOSE

Mediverse is designed to solve the critical problem of fragmented medical histories by creating a secure, patient-centric digital healthcare ecosystem. Every patient is assigned a unique, persistent **Mediverse Health ID** generated by the backend API. All authorized medical interactions—consultations, prescriptions, laboratory reports, hospital admissions, discharge summaries, certificates, and uploaded medical documents—are linked into a unified digital healthcare timeline owned and controlled by the patient.

## 3. FINAL USER ROLES (6 ROLES)

1. **PATIENT** (Platform: Flutter Mobile App)
   - Manages personal health profile, views health timeline, uploads documents, views prescriptions/reports/appointments, manages consent/permissions, views access history, uses **Patient AI Assistant**, configures emergency info.
2. **EMERGENCY** (Platform: Flutter Mobile App)
   - Read-only access to vital emergency information (blood group, emergency contacts, critical allergies, active medications, key conditions) during medical emergencies under strict audit logging.
3. **DOCTOR** (Platform: Web Portal - React)
   - Identifies patients via Health ID or secure QR reference, accesses authorized records, conducts consultations, writes digital prescriptions, adds clinical notes, uploads medical documents, reviews RAG summaries from the **Mediverse Healthcare Record Agent**.
4. **MEDICAL** (Platform: Web Portal - React)
   - Represents authorized hospitals and medical organizations. Manages admissions, clinical treatments, discharge summaries, hospital document uploads, and authorized staff accounts.
5. **LAB** (Platform: Web Portal - React)
   - Identifies patients, creates diagnostic test records, uploads lab reports/results, links reports to patient timelines with purpose-bound minimal data access.
6. **ADMIN** (Platform: Web Portal - React)
   - Administrative and security oversight role. Verifies healthcare providers (Doctor, Medical, Lab), manages account lifecycles (PENDING, ACTIVE, REJECTED, DEACTIVATED), monitors audit logs, manages system configuration. **Admin READ access to Patient Profile is strictly limited to administrative identity/account info required for account management. Admin has NO access to medical history, diagnoses, consult notes, prescriptions, lab reports, clinical timelines, or private medical documents.**

## 6. CORE ARCHITECTURAL CONCEPTS

### 6.1 Mediverse Health ID Concept
- **Generation:** Server-side generated during patient registration via Spring Boot backend.
- **Format:** `MV-YYYY-XXXXXXXX` is a project-defined unique Mediverse Health ID format.
- **Attributes:** Unique, persistent, immutable, database-constrained.
- **Security Boundary:** The Health ID identifies the patient; it **DOES NOT** grant automatic or unrestricted access to medical records.
- **ID Distinction:** Internal User Database ID (`user_id` `CHAR(36)`) is decoupled from public `Mediverse Health ID`.
- **QR Code Reference:** Mobile QR codes encode a secure patient Health ID reference token, NOT raw medical history or sensitive clinical details.

### 6.2 Patient-Centric Health Record Model
- Every consultation, lab result, prescription, admission, and document upload attaches to the central patient timeline.
- Providers access patient records only under active authorization, consent, or emergency override rules.

### 6.3 Dual Storage Architecture
- **Supabase Storage:** Stores raw files (PDFs, JPEGs, PNGs, scanned reports, medical images).
- **MySQL Database:** Stores structured domain metadata (File ID, Patient ID, Uploader Role, File Path, File Name, Mime Type, Hash, Upload Timestamp, Consent Status).

### 6.4 Authentication & Authorization Flow
```
Client Login Request 
  ↳ Spring Boot Credential & BCrypt Hash Validation 
  ↳ Role Extraction & JWT Signature 
  ↳ Subsequent API Request with Bearer Token 
  ↳ JWT Filter & Signature Validation 
  ↳ RBAC Security Check 
  ↳ Patient Consent & Emergency Access Rules Verification 
  ↳ Resource Execution / Denial 
  ↳ Append-only, Tamper-Resistant Audit Log Recording
```

### 6.5 Dual AI Architecture & Boundaries
1. **Patient AI Assistant:** Serves the patient on Flutter Mobile using information the patient is authorized to access. Must not provide unrestricted clinical information and cannot diagnose or prescribe.
2. **Mediverse Healthcare Record Agent:** Assists authorized healthcare professionals on the React Web Portal by retrieving authorized patient records and performing source-grounded RAG summarization under RBAC and consent. Must not diagnose, prescribe, or make autonomous treatment decisions.

## 7. MANDATORY DEVELOPMENT RULES FOR FUTURE AGENTS

1. **No Architecture Deviations:** Do not alter the 3-tier architecture (Mobile/Web -> Spring Boot API -> MySQL / Supabase).
2. **Role Integrity:** Do not add, remove, or rename any of the 6 approved roles without explicit approval.
3. **Database Guardrails:** Mobile and Web frontends must NEVER connect directly to MySQL or Supabase directly. All operations pass through Spring Boot API.
4. **Health ID Scope:** Never use Health ID as an authentication token or authorization key.
5. **Password Handling:** Plaintext passwords must NEVER be saved, printed in logs, or exposed in API responses. Use BCrypt.
6. **Private File Storage:** Medical storage buckets must remain private; pre-signed timed URLs or backend proxying must be used for view access.
7. **Admin Access Boundary:** Admin must NEVER be given view access to medical histories, clinical notes, prescriptions, lab results, or clinical documents.
8. **Audit Logging Terminology:** Audit logs are append-only and tamper-resistant; avoid unverified claims of cryptographic non-repudiation unless explicitly designed.
9. **AI Boundaries:** AI engines function strictly as source-grounded tools. AI must never issue direct clinical decisions, diagnoses, or prescriptions.
10. **Synthetic Data Only:** Real patient data (PHI/PII) must never be imported. Use synthetic medical datasets for testing.
