## 7.1 HEALTH ID CORE CONCEPT & PURPOSE

The **Mediverse Health ID** is a unique, persistent, server-side generated identifier assigned to every patient upon registration. It serves as the master index for unifying a patient's medical records across doctors, hospitals, laboratories, and mobile portals.

```
+-----------------------------------------------------------------------------------+
|                        HEALTH ID ARCHITECTURAL BOUNDARIES                         |
+-----------------------------------------------------------------------------------+
| [X] GENERATED EXCLUSIVELY BY BACKEND API  (Spring Boot `HealthIdService`)         |
| [X] GLOBALLY UNIQUE & DATABASE-CONSTRAINED (`UNIQUE INDEX` in MySQL)               |
| [X] IMMUTABLE AFTER CREATION              (Never changes for patient lifetime)   |
| [X] DECOUPLED FROM INTERNAL USER ID       (`user_id` CHAR(36) UUID != `health_id`)|
| [X] LOOKUP INDEX ONLY                     (DOES NOT GRANT AUTOMATIC DATA ACCESS) |
| [X] SECURE QR CODE REFERENCE              (Encodes token, NOT raw medical text)   |
+-----------------------------------------------------------------------------------+
```

## 7.2 HEALTH ID FORMAT & GENERATION SPECIFICATION

- **Format Standard:** `MV-YYYY-XXXXXXXX is a project-defined unique Mediverse Health ID format.` (e.g. `MV-2026-8A3F9B12`).
  - Prefix: `MV` (Mediverse Ecosystem Identifier).
  - Year Segment: 4-digit registration year (e.g. `2026`).
  - Entropy Segment: 8-character cryptographically secure alphanumeric string generated via `SecureRandom`.
- **Generation Workflow:**
  1. Patient submits registration via Flutter Mobile App.
  2. Spring Boot backend creates `User` account entity with assigned primary role (`PATIENT`).
  3. `HealthIdService` generates candidate Health ID string.
  4. Backend verifies uniqueness against `health_id_registry` in MySQL.
  5. Backend persists `health_id` and attaches it to `patient_profiles`.
  6. Health ID is returned in registration response and embedded in JWT token.

## 7.3 HEALTH ID LIFECYCLE & LOOKUP MECHANICS

```
+-----------------------------------------------------------------------------------+
|                           HEALTH ID LOOKUP & ACCESS FLOW                          |
+-----------------------------------------------------------------------------------+
| Provider Enters Health ID / Scans QR -> Spring Boot API Request                    |
|   ↳ Step 1: Health ID Lookup in `patient_profiles` -> Extract `patient_id`        |
|   ↳ Step 2: RBAC Check -> Is Provider Account Status `ACTIVE`?                    |
|   ↳ Step 3: Consent Check -> Query `patient_consents` for Active Grant            |
|       ├─ Active Consent Found -> ALLOW Access & Log Audit                         |
|       └─ No Active Consent   -> DENY Access (403 Forbidden: Consent Required)    |
+-----------------------------------------------------------------------------------+
```

---

## 7.4 SECURE QR CODE REPRESENTATION

- **QR Code Payload:** Encodes a signed JSON reference payload containing:
  - `healthId`: Patient Mediverse Health ID.
  - `issuedAt`: Issue timestamp.
  - `signature`: HMAC-SHA256 signature generated by Spring Boot server secret key.
- **Security Rule:** **The QR code payload MUST NEVER encode raw medical history, diagnoses, prescriptions, lab values, or personal notes.** It acts solely as a verified physical presentation lookup token.
